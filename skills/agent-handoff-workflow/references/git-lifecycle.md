# Git 操作细则

这里的 dev/main 代表实际的开发分支/稳定分支，remote 代表已核实的远程。命令示例用于说明，不是可直接整段执行的脚本。先确认目录、分支、用户授权和当前 shell。

## 只读检查工具

脚本 [inspect_handoff.py](../scripts/inspect_handoff.py) 需要 Python 3.9+ 和 Git，无第三方库。将下面的 Skill/项目目录替换为真实路径，沿用现有可用 Python 环境：

```text
python "Skill目录/scripts/inspect_handoff.py" --repo "项目目录" --dev dev --stable main
python "Skill目录/scripts/inspect_handoff.py" --repo "项目目录" --check-remote --json
python "Skill目录/scripts/inspect_handoff.py" --repo "项目目录" --check-remote --expect 完整提交哈希
```

- 默认不联网，显示本地状态和明确标为“可能过期”的追踪引用。`--check-remote` 只用 ls-remote 读取真实分支指向，不 fetch、不改引用；远程新提交尚不在本地时会报告无法比较，之后按接手规则另行获取。
- 分支名用 `--dev`、`--stable` 指定；从各分支 upstream 推导远程及远程分支名，没有 upstream 时可显式 `--remote 已配置名称`，此时无配置映射的分支按同名分支查询。不猜测 origin 或访问未指定的任意 URL。
- `--expect` 接受预期的完整提交哈希，核实对象和开发历史归属；`--task` 按精确任务 ID 筛选最近快照。仅扫描最近 100 个提交、最多列出 5 个 checkpoint，找不到不等于全历史不存在。
- JSON 的 `handoff.state` 为 blocked、unverified 或 git_history_verified；最后一种只证明当前开发提交与观察到的远程一致，不能证明业务验收、忽略资产、运行环境或其他设备未推送内容。稳定分支同步单独看 `branches.stable.remote`，不能由 dev 同步推断 main 交付完成。
- 退出码 0 表示检查执行完毕，即使报告阻塞；退出码 2 表示调用/检查失败。自动读取者必须检查 JSON 字段，不把退出码 0 当成验收通过。
- 工具不暂存、提交、合并、回退、清理或修复，不输出配置中的远程 URL/凭据。人工核对文档、资产和授权仍然必要。

维护工具时运行 [隔离回归测试](../scripts/tests/test_inspect_handoff.py)：`python -B "Skill目录/scripts/tests/test_inspect_handoff.py"`。测试只在新建临时目录中使用本地 bare remote；`HANDOFF_TEST_ROOT` 可指定临时目录父路径。夹具和操作日志会保留，不覆盖已有仓库。

## 1. 建立或接续开发分支

- 检查 status、分支、Worktree、最近历史及未结束的 Git 操作。无首次提交时先处理已授权基线；不要误报仓库损坏，也不能假定可直接创建 Worktree。
- 沿用已有开发/稳定分支名称与项目策略；新采用本流程时，dev 从用户认可的基线建立。已有 dev 先检查归属与历史，不重建或覆盖。
- main 只接收验收后的交付；低风险文档修改也默认从 dev 开始。明确的紧急修复可单独从 main 分出，验证交付后把修复同步回 dev。
- 单人顺序任务可在 dev 工作。并行或独立试验使用各自任务分支和 Worktree；遵守宿主托管 Worktree 的创建/归档机制。任务分支与 dev 约定一个集成人。
- 开始长任务前判断期间是否还要交付其他已完成成果；如需要，提前将长任务放独立任务分支。已经混入 dev 的未完成工作先明确发布范围和依赖，不为赶交付猜选提交或强行回退。
- Worktree 不复制原目录未提交和被忽略内容，也不隔离数据库、端口等运行资源；依赖这些内容时明确处理。
- 临时任务分支完成后，优先以保留原提交的普通合并/快进方式合入 dev，使 checkpoint 成为 dev 的祖先。合入 dev 依项目授权且需相关验证；未验证的试验不能自动混入共享开发基线。
- 修改 Skill 不自动迁移已有项目分支和 ADR。迁移时记录当前基线、实际分支、集成方式和授权，保留旧记录。

## 2. checkpoint 以 Git 历史为准

### 什么时候提交

一个有意义的阶段通过必要验证后，按本地提交授权创建 checkpoint；不为每次工具调用创建提交。提交前保护用户已有暂存安排，明确选择本任务文件，检查最终暂存差异、敏感信息和资产政策。已批准的二进制资产例外按项目约定处理。

验证必须覆盖实际拟提交内容。存在部分暂存/部分提交时，不能借用留在工作区而未提交的代码来证明测试通过。必要检查失败或阻塞时保存交接或已授权 WIP，不创建稳定 checkpoint；原有失败也不能自行豁免必需门禁。

推荐提交说明：

```text
checkpoint(TASK-007): CP-01 完成图片上传

验证：上传接口相关测试通过；无跳过。
范围：仅上传流程；透明背景导出尚未实现。
```

提交正文记录方法、环境或必要证据位置即可，不写提交自身哈希。哈希由 Git 生成，验证结果对应实际提交内容。未完成提交用 `wip(TASK-007): 当前状态`，明确失败与缺口，不与 checkpoint 混称。

### 怎么查询

对已核实的开发分支可使用：

```text
git log dev --format="%h %s" --grep="^checkpoint(TASK-007): CP-"
```

该示例查找任务前缀；需要 CP-01 时还要核对完整主题、完整提交哈希、任务和内容，不能把 CP-010 当作 CP-01。尚未合入 dev 的任务快照应查对应任务分支。旧格式提交或旧账本按已知哈希核验，不为统一格式重写历史。

创建 CP 编号前查看相关本地及已更新的远程任务历史；并行任务由负责人协调编号。发现重复时使用完整哈希区分，后续编号纠正，不重写已共享提交。

### 工单只记重要信息

- 不逐条抄录每个 checkpoint，不维护另一份与 Git 竞争的完整账本，也不为填自身哈希形成递归提交。
- 工单保留关键里程碑和验收证据、开发/任务分支、最近核对的基线、同步状态与下一步。必要时引用某个已存在提交，明确这是“核对时的记录”，不是永远最新的 HEAD。
- 完成项与验证说明可随对应代码一起提交；代码提交后的确认信息可在最终报告中给出，无需再专门修改文档去追赶最新哈希。
- 旧快照账本保留为历史索引。记录与 Git 不符时，以实际对象、历史和工作区为准，报告并修正已确认差异；对象不存在时不假装恢复成功。

## 3. 换设备前后的同步

### 离开当前设备前

1. 处理可归属本任务的修改并保存必要交接记录；敏感文件不进 Git。未提交、未跟踪及重要忽略文件需要单独处理，不假定推送包含它们。
2. 有同步授权时，推送明确的远程开发分支；仍只在任务分支上的 checkpoint 要推送对应任务分支，或先按授权保留历史合入 dev。仅推 main 无法备份 Squash 前的开发历史。
3. push 成功后核对远程分支实际指向，必要时确认所需 CP 是该远程提交的祖先。记录“核对时间＋分支＋已同步提交”；分支继续变化后此记录只是历史证据。
4. push 失败或未授权时报告“仅本地已保存，换设备未就绪”，保留现场。不自动强推、换远程或推所有标签。无远程时可按明确要求用 Git bundle 等离线方式转移，并在接收端验证；这同样不包含未提交/忽略文件。

### 到新设备后

1. 确认仓库来源和实际远程，获取相关分支历史；浅克隆/部分历史缺失时补取所需历史再核验，不能把缺失直接判作旧快照已删除。
2. 比较本地 dev 与更新后的远程开发分支；不能仅依靠陈旧的追踪引用或工单。示例 `git rev-list --left-right --count dev...origin/dev` 的左边表示本地独有，右边表示远程独有，origin/dev 必须替换成真实追踪分支。
3. 本地干净且只落后时可快进同步；本地领先时保留尚未推送内容；双方均有独有提交时先审查并按项目策略集成，不 reset 覆盖或自动 rebase 共享历史。有未提交修改先保护和区分归属。
4. 核对当前分支、实际提交、CP 是否可解析且属于正确历史，以及运行环境/必要资产。文件和测试支持工单状态后再继续。

新设备与远程一致，只能证明拿到了远程已有历史，无法证明旧设备没有未推送工作。交接时有预期任务/CP/提交就核对它；来源记录不全或旧设备离线时明确这一限制，只继续已确认不依赖缺失内容的工作，不把“与 origin/dev 一致”当作所有设备全部同步的证明。

dev 长期保留、保持历史并实际同步，才能持续提供跨设备恢复点。分支名称、哈希文本和本地标签本身都不是远程备份。

## 4. 把完整功能交付到 main

默认采用“dev 保存过程，main Squash 保存完整成果”，并把 main 合回 dev。已有项目使用普通 merge/PR 等方式时遵循其已接受策略，不擅自改写历史。

1. 确认本批交付范围、main/dev 实际提交、分支占用和合并授权。检查整个待集成差异，而不是只看当前工单；dev 含 WIP 或未完成功能时不能整支交付。需要选择性交付时明确独立发布范围与方案，不能猜测 cherry-pick 哪些提交。
2. 若 main 有 dev 尚未包含的修复，先正常合并到 dev 并验证。准备交付后固定本批 dev 提交作为源；多人使用时协调集成窗口，不能验证一个版本后却合并移动后的另一版本。
3. 在合适的干净集成工作区，将已核实的源提交 Squash 到 main，审查并验证最终集成内容。必要验证失败/阻塞时停止合并完成与后续推送，先修复范围内问题并复测。必须提交后验证时可保留本地提交但停止交付；一般授权不等于接受失败例外。
4. 在授权内完成 main 的正式提交。提交信息记录来源 dev 的完整哈希和交付范围，例如正文 `Development-source: 实际完整哈希`。main 的提交与开发快照哈希不同是 Squash 的正常结果。
5. 在同一次本地交付中，把新 main 提交普通合并回 dev（例如在正确工作区执行 merge），保留 dev 原有历史；同范围的流程合并授权覆盖这一步，不逐次重新询问。若 dev 已继续变化，保护新工作并核验合并结果，禁止强行重置 dev。尚未继续开发时，两支的文件树应一致，且 main 应是 dev 的祖先；有后续开发时检查新增差异符合预期。
6. 这一“合回 dev”步骤让下一轮从新的共同基线开始，避免重复 Squash 时携带旧差异；不能遗漏。冲突或验证失败则报告“main 本地提交已创建，开发分支同步未完成”，保留现场并解决后再宣布流程完成。
7. 按实际授权分别推送 main/dev；推送 dev 的权限不能代替推送 main 的权限。可用且获授权时原子推送两支；否则分开推送并逐项核实。一支失败要报告实际部分同步状态，不声称两支均完成。
8. 更新任务关键成果和交付状态即可，不生成新的完整快照账本；继续下一轮开发前确认分支关系与必要验证。

普通合并方式保留提交祖先关系，不需要额外 Squash 同步流程；报告中明确实际方式。main 紧急修复同样要回流 dev，防止后续交付覆盖。

### 交付中断后从哪里继续

重新接手先读取工作区、暂存差异、Git 操作标记、相关提交正文/差异、祖先关系和实际远程指向。结合已验收源提交、`Development-source` 与工单辨认本次交付；提交说明只是线索，仍要核实实际代码及验证。线索冲突或有多个候选时只暂停有歧义的步骤，不重复创建交付。

| 实际现场 | 接续动作 |
| --- | --- |
| Squash 已生成暂存内容，尚未提交 | 核对完整暂存差异是否属于固定的验收源；区分用户原有暂存内容，继续对应验证和提交。没有 MERGE_HEAD 不代表没有待处理 Squash；不再次执行 merge，也不整体取消暂存 |
| main 正式提交已存在，尚未合回 dev | 核实真实交付提交、内容与来源，不再 Squash；在合适且干净的开发工作区完成正常回流 |
| 合回 dev 时冲突或验证失败 | 保留冲突、MERGE_HEAD/暂存和日志；接续本次合并的解决与验证。不能发起第二次 merge、把 reset 当成修复，或静默中止当前操作 |
| 回流完成但未推送 | 核对 main 已在 dev 历史中；有后续开发时区分新增差异。验证和授权仍适用后，只继续缺少的同步步骤 |
| 一条分支推送成功，另一条失败 | 读取实际远程，明确各自已同步提交；只重试仍未完成且已获授权的目标。远程已前进时先检查并处理历史差异，不强推覆盖 |
| 两条分支都已同步 | 核对预期交付确已到达；完成交接记录，不再生成同一成果的 Squash 或回流提交 |

源码、目标分支或验收范围发生实质变化时重新验证受影响部分。不能因为上一次曾通过就沿用过期结果，也不因重复接手而重新请求仍有效的同范围授权。只读工具提供事实，不能替代对这张表的交付归属判断。

## 5. 恢复阶段与清理

先根据任务＋CP 编号查实际提交并核实对象可用性、所属历史和恢复范围。仅查看旧版用 diff/show 或独立 Worktree；只恢复几个文件则处理明确路径；共享 dev/main 上撤销效果通常追加新提交。单个 Git revert 不等于把整个项目恢复到某快照，恢复后必须核验实际文件树和相关行为。

改变现场前检查暂存、未提交、未跟踪和重要忽略文件，建立适配数据的可验证保护。引用不能保存未提交内容，纯 patch 不能覆盖所有二进制/未跟踪文件。不要把敏感资产为了备份提交进历史。已明确的恢复意图不重复询问，范围不清或影响他人工作时先核实。

`reset --hard` 可能丢弃改动及阻挡检出的未跟踪文件；不作为默认恢复动作。不得擅自 reset/rebase/强推共享 dev，或执行 clean 清理用户现场。恢复后保留旧事件记录并记录新状态。

main 和 dev 都是长期分支，不在任务结束时删除。临时任务分支/Worktree 清理前：
- 确认必要 checkpoint 已成为 dev 的祖先，且若要换设备，已经在接收端可取得的远程历史中；不能只核对合并后的文件内容相同。
- 若项目特殊策略将任务分支 Squash 到 dev，先保留必要原始历史的引用并按授权同步，或保留任务分支；没有必要每个 CP 都建标签。
- 检查未提交、未跟踪、重要忽略资产和运行进程；保存唯一有价值产物、最终接续记录。
- 只清理本任务拥有且不再需要的临时资源，使用宿主归档/Git Worktree 命令；不直接递归删目录，不强制绕过未知状态。无法证明安全就保留并说明。
