# AI 项目接手与交接

这个 Skill 帮助 AI 记住项目做到哪里，并让另一个会话或另一台设备接着做。

**采用本流程后：日常开发在长期开发分支 `dev`；完成并验收的功能进入稳定分支 `main`；快照从 Git 历史查，工单只写关键进度和下一步。** 项目已有其他分支名称时沿用名称；修改 Skill 本身不等于迁移当前业务项目。

## 一、平时怎样使用

| 用户请求 | AI 要做的事 |
| --- | --- |
| “给项目建立接手规范” | 检查已有文件，再补齐状态、决策和任务文档；不覆盖用户内容 |
| “接手这个任务” | 读项目状态和当前工单，核对实际代码、分支与同步情况，再继续下一步 |
| “保存当前进度” | 检查改动和授权；验证通过可存 checkpoint，未完成则如实保存交接记录或已授权的 WIP |
| “换设备继续” | 核对开发分支是否已同步、新设备是否已取得相同提交，以及有无仅本机文件 |
| “功能完成，合并到主分支” | 检查整批待交付内容，验证合并结果，按已有授权合并和推送 |
| “回到某个快照” | 从 Git 找到真实提交，保护当前修改，再按需要恢复 |
| 只解释概念或审查 Skill | 只分析，不自动初始化项目、建工单或运行业务测试 |

初始化/接手异常时读 [接手细则](references/continuity.md)。操作分支、checkpoint、同步、合并或恢复前，读 [Git 操作细则](references/git-lifecycle.md) 的对应部分。无需每次加载全部模板。

## 二、两条长期分支各做什么

| 分支 | 用途 |
| --- | --- |
| `dev` 开发分支 | 保存开发过程与 checkpoint，长期保留；获得推送授权后同步到远程 |
| `main` 稳定分支 | 只接收完成并验收的交付成果，日常开发不直接写入 |
| 临时任务分支（需要时） | 用于并行、试验或单独隔离；从开发基线分出，完成后保留提交历史合入 dev |

单人顺序开发通常直接在 dev 上进行，不为每个小任务增加分支。多会话同时写入时，各自使用独立任务分支和 Worktree（独立工作目录）；约定公共文件、接口、端口/数据库等资源与集成人，不同时写同一目录，也不自动启动其他 Agent。

如果下一项功能可能长期未完成，而期间仍要交付其他成果，应提前使用任务分支；避免把已完成功能和长期试验混在 dev 后再临时拆分。

默认交付方式为：验收一批完整的 dev 改动 → Squash 到 main → 将新的 main 正常合并回 dev。最后一步保留共同历史，支持下一轮交付；不得通过重置 dev 来“对齐”。dev 中混有未完成功能时不能整支交付。项目已有合并规则时保留该规则，迁移需有对应任务与授权。

Squash 是把本批开发成果在 main 上保存为一次正式提交；“合回 dev”是把这次正式交付记录带回开发分支，原有阶段快照仍然保留。

## 三、快照怎样保存和查找

- **checkpoint** 是通过本阶段必要验证的 Git 提交，例如 `checkpoint(TASK-007): CP-01 完成图片上传`。提交正文简记验证方法和结果，Git 自带的提交哈希定位这一版代码。
- **WIP** 是已授权保存的未完成提交，明确记录失败与缺口；不能称为稳定 checkpoint。
- **工单不再维护每个 checkpoint 的完整账本**。只记录关键里程碑、必要证据和下一步；需要全部快照时从对应分支的 Git 历史查询。旧账本保留为历史索引，使用前核实。
- CP 编号只在任务范围内标识阶段；实际提交哈希才是最终定位依据。编号重复或找不到时先查明，不能猜选。
- dev 保留历史不等于已跨设备保存。必须把需要的开发历史同步出去，并在新设备取得；推送 main 不能替代推送 dev。
- 对共享 dev 不自行 rebase、reset 或强推。要撤销效果通常追加新提交；保护历史中的恢复点。

## 四、开始工作前检查什么

1. 确认实际项目根目录，读取适用的 `AGENTS.md`、`docs/PROJECT_STATUS.md`、当前有效决策和本次工单；只按明确依赖扩展阅读。核对项目记录的工作流版本和特例；旧版或未标版本先比较差异，不直接套新版覆盖。
2. 核对当前分支/Worktree、最近提交、已有改动及未结束的 Git 操作。跨设备接手时还核对远程开发分支和本地领先/落后情况；不能只看工单。
3. 检查与任务有关的代码、运行环境和验证基线。文档说完成但代码/测试不支持时，记录差异，不照抄完成状态。
4. 确认下一步仍符合用户最新目标后继续。缺文件、失败基线或环境不足只阻塞依赖它们的动作；保留用户修改，不自动清理或顺带提交。

可用 [只读接手检查工具](scripts/inspect_handoff.py) 统一汇总分支、工作区、同步情况和最近快照。默认只读本地；显式 `--check-remote` 才查询远程，不执行 fetch 或修复。使用方法和结果边界见 [Git 操作细则](references/git-lifecycle.md)。没有 Python 时按同样规则人工核对，不为检查工具强制安装依赖。

若上次交付中断，先判断已做到哪一步，再继续剩余动作；不从头重做 Squash。对应恢复表也在 Git 操作细则中。

## 五、权限和验证

遵守宿主指令优先级和工具权限；Skill 是默认流程，不覆盖用户明确指令或已接受的项目约定。

| 操作 | 执行条件 |
| --- | --- |
| 任务范围内的编辑、检查与必要分支准备 | 按任务授权执行 |
| 本地 checkpoint、WIP 或文档提交 | 用户已授权，或用户已接受的项目政策明确允许该类提交 |
| 合并 main | 有覆盖本次交付的明确授权 |
| 推送 dev、推送 main、发布 | 各按明确目标与动作授权；允许同步 dev 不等于允许发布 main |
| 丢弃改动或重写共享历史 | 不从自动提交权限推导，核实具体意图和保护方式 |

已有同范围授权持续有效，不重复询问。授权可覆盖本任务后续 dev 同步，但需记录来源和范围；工单记录本身不产生权限。未获提交或推送授权时继续可完成的编辑、验证和交接，说明哪些内容仅在本机。

验证按变更风险和项目要求执行，分别记录通过、失败、阻塞、未执行和不适用。部分提交要验证实际拟提交内容；不能用未提交代码的结果证明提交通过。必要验收未通过不能宣布完成；最终集成验证失败时停止后续交付，先修复复测。一般合并/推送授权不代表用户接受失败例外。

## 六、结束前留下什么

- 当前目标、关键成果和验证证据；工单的下一步应能直接执行。
- 实际开发分支、最近核对的提交、未提交内容及本地/远程同步情况。
- 原有失败、新增问题、阻塞原因和恢复条件；未完成也可以诚实交接。
- 核心方案保存到 `docs/designs/`，重要决策记录在 `docs/DECISIONS.md`；正式图表和复用工具按用途转正。已有等价目录可沿用。
- 可丢弃脚本放 `.ai/scratch/`，预览放 `.ai/artifacts/`，由 Git 忽略；唯一有价值的产物不能只留这里或 IDE 私有缓存。
- 分开报告本机保存、已提交、已同步 dev、已合并 main、已推送 main、已发布。本地引用和忽略文件不能保证换设备可用。

任务状态可用“待开始、进行中、待验收、已验收、已合入 dev、已交付 main”；暂停/阻塞附恢复条件。无代码任务按实际交付状态记录，不强制合并。新 ADR 可正式替代旧决策，保留理由和来源；不将推测写成已批准决策。
